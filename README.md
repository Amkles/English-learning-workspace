# Prompt Lab · 提示词工程实验集

> 把一段长提示词，做成**能跑、能测、能改**的东西。

这里存放我用提示词工程产出的完整项目。每个项目都不是「一段提示词 + 一个 demo」，而是四件东西配套：**提示词原文、可运行产物、断言式测试、设计文档**。

## 提示词：[PROMPT.md](PROMPT.md)

完整提示词放在**仓库根目录**，不打进子文件夹——它是这个仓库的主角，打开就该看到。

那份提示词约 6900 字、14 个小节，结构是四段：**硬性约束 → 页面与交互 → 抽取算法 → 验收与易错点**。

三段经验值得单独说：

**一、把提示词当规格写，不当愿望写。**
「做一个好看的打卡应用」没法验收；「五项全部达标才算当天成功，达标 1→4 项颜色逐级加深，5 项全清换紫色徽标」可以验收。约束越具体，返工越少。

**二、难点在约束和边界，不在功能列表。**
单文件应用的功能都差不多，真正决定质量的是那几十条「不许做什么」：不许引 CDN、不许用 emoji 当图标、词性缺失时不许留空占位、解析 0 条时不许清空原素材。

**三、把易错点写进提示词。**
模型不会自己意识到「冷却天数写死会在池子小时天天重复」「换题库不升版本号会让卡片变空白」。这些坑必须点名，否则一定踩。所以提示词末尾有 11 条验收用例和 6 条易错点。

## 这个仓库在试什么

写了几个长提示词之后，我发现质量差距不在这几件事上：提示词漂不漂亮、模型强不强、写了几轮。差距在下面四条：

**产物必须能被测试。** 能跑起来不等于对。抽取逻辑跑了 400 天模拟，验证没有空手、没有提前回头、覆盖完整——这类问题肉眼根本看不出来，只有断言能抓住。

**内容池要真。** 占位符（"Article 1"、"示例题目"）会让产物失去价值，还会掩盖真实排版问题：真实标题长度参差、真实视频时长不一、真实链接会失效。所以内容池全部来自可访问的真实来源，链接逐条校验过。

**产物与源码必须同步。** 有构建步骤的项目，产物要能被 CI 重建后逐字节比对。构建不可重复，就说明产物和源码已经不是一回事了。

**不采集数据。** 所有项目本地存档，不上报、不埋点、不要求注册。

## 修改与贡献

这是个人实验仓库，欢迎提 Issue 指错、提 PR 加项目。

### 六条硬约束（任何项目都不能破）

1. **产物要能独立运行**。单文件就真的单文件，不偷偷引 CDN；引了依赖就在 README 里写清装什么。
2. **内容池不许放占位符**。「示例文章 1」「题目待补充」不算内容，只会掩盖排版问题。
3. **不采集用户数据**。本地存档放 `localStorage`，不上报、不埋点、不要求注册。
4. **不提交密钥**。API key、token、cookie 一律不进仓库。
5. **不写个人隐私**。真实姓名、学校、导师、手机号、身份证号不进任何文件，包括测试数据和截图。
6. **产物与源码必须同步**。改源码不重新构建就提交，CI 会红。

### 新增项目

```
<slug>/
├── README.md            必备：是什么、怎么跑、截图、已知限制
├── src/                 源码（单文件项目可省略）
├── data/                内容池（如有）
├── tests/               断言式测试（有逻辑就要有）
├── docs/                设计文档与截图
└── index.html           产物（有构建的话）
```

然后在根 `README.md` 的项目表格加一行，在提示词 `PROMPT.md` 里追加对应章节或另开文件，在 `.github/workflows/` 加一个测试 job（可复制 `cet6-daily-test.yml`）。

### 测试怎么写

- **断言行为，不断言外观**。外观交给截图人工看，逻辑交给断言。
- **用长时间跨度压测**。抽取类逻辑跑 400 天，能暴露「前 30 天正常、之后开始重复」。
- **测边界，不测主流程**。主流程肉眼能看出来，边界不能：池子比需求小、解析结果为 0、跨月、跨年、同一天刷新两次。
- 测试不要依赖真实日期的副作用；要么注入日期，要么开头把状态清干净。

### 代码风格

注释和提交信息用中文，术语保留英文原文（`localStorage`、`Fisher–Yates`）。提交信息第一行 ≤ 50 字，正文说「为什么改」；一次提交做一件事，重构和改功能不混在一起。

### 提 PR 之前

```bash
cd cet6-daily
python tools/build.py          # 有构建的话，确认产物可重复
cd tests && npm ci && npm test # 三套测试全绿
```

CI 会检查两件事：产物是否与源码一致（重建后 `git diff` 必须为空）、三套测试是否通过。

### 报告问题

Issue 里写清：浏览器与版本、复现步骤、期望结果、实际结果。涉及抽取逻辑的，附上当天的存档导出（设置 → 导出 JSON），不要贴截图代替文字。

## 已知限制

- **仓库整体是中文的**，代码注释、提交信息、文档都以中文为主
- 每个项目各自独立、各带依赖，没有统一的 monorepo 工具链——这是故意的，单文件产物不该被构建系统绑架
- Pages 一次只能发布一个站点，多个项目要分别配置
