# Prompt Lab · 提示词工程实验集

> 把一段长提示词，做成**能跑、能测、能改**的东西。

这个仓库存放我用提示词工程（prompt engineering）产出的完整项目。每个项目都不是「一段提示词 + 一个 demo」，而是四件东西配套：

| 交付物 | 作用 |
|---|---|
| `docs/prompt.md` | 写这份产物时用的完整提示词，原样公开 |
| 可运行产物 | 打开就能用，不依赖我的环境和账号 |
| `tests/` | 把「对不对」交给断言，不靠肉眼 |
| 设计文档 | 关键算法、数据结构、取舍理由 |

## 这个仓库在试什么

写了几个长提示词之后，我慢慢发现质量差距不在「提示词写得多漂亮」，而在这四件事上。这个仓库的每个项目都按这四条做：

**一、把提示词当规格写，不当愿望写。**
「做一个好看的打卡应用」没法验收；「五项全部达标才算当天成功，达标 1→4 项颜色逐级加深，5 项全清换紫色徽标」可以验收。规格越具体，返工越少。

**二、提前把易错点写进提示词。**
模型不会自己意识到「冷却天数写死会在池子小时天天重复」「解析 0 条时不能当清空处理」。这些坑必须在提示词里点名，否则一定踩。每个项目的 `docs/prompt.md` 末尾都有一节「易错点」。

**三、产物必须能被测试。**
能跑起来不等于对。六级打卡台写了 400 天的抽取压力测试，验证没有空手、没有提前回头、覆盖完整——这类问题肉眼根本看不出来，只有断言能抓住。

**四、内容池要真。**
占位符（"Article 1"、"示例题目"）会让整个产物失去价值，也会掩盖真实的排版问题：真实标题长度参差、真实视频时长不一、真实链接会失效。所以内容池全部来自可访问的真实来源，链接逐条校验过。

## 目录约定

```
prompt-lab/
├── README.md                    # 本文件：仓库总览
├── LICENSE
├── CONTRIBUTING.md              # 新增项目的规矩
├── .github/workflows/
│   ├── pages.yml                # 部署 projects/*/index.html 到 Pages
│   └── cet6-daily-test.yml      # 项目 CI
└── projects/
    └── cet6-daily/              # 一个项目一个文件夹，自成一体
        ├── README.md
        ├── docs/prompt.md       # 原始提示词
        ├── docs/*.md            # 算法、数据模型
        ├── docs/screenshots/
        ├── src/                 # 源码
        ├── data/                # 内容池
        ├── tests/               # 验收用例
        ├── tools/               # 构建与抓取脚本
        └── index.html           # 构建产物
```

项目文件夹内部的路径引用一律用相对路径，所以整体搬动目录、单独 fork 某个项目都不会断链。

## 新增一个项目

1. `projects/<slug>/`，slug 用小写英文短横线
2. 必备：`README.md`（做什么、怎么跑、已知限制）、`docs/prompt.md`（原始提示词）
3. 有构建的，产物要能被 CI 重建并比对，避免仓库里的产物和源码走偏
4. 有逻辑的，`tests/` 里放断言而不是截图
5. 在根 `README.md` 的表格里加一行
6. 需要线上预览的，在 `.github/workflows/pages.yml` 里加一个 job

细则见 [CONTRIBUTING.md](CONTRIBUTING.md)。

## 已知限制

- **仓库整体是中文的**，代码注释、提交信息、文档都以中文为主
- 每个项目各自独立、各带依赖，没有统一的 monorepo 工具链（这是故意的：单文件产物不该被构建系统绑架）
- Pages 一次只能发布一个站点，多个项目要分别配置
